<objective>
Build the beam-search sequencer — the product. Given a bag of candidate tracks it returns the
longest BPM-legal run that uses each physical record at most once, tie-broken on harmonic
smoothness, plus a reason for every record it had to leave out.

Purpose: SEQ-02, SEQ-03, SEQ-04, SEQ-06. This is the app's uncontested differentiator. Label
OCR is a commodity; nothing else models one-track-per-physical-record. It is also the piece
that is fully testable today with no camera, no network and no iOS 27 SDK, which is why it is
front-loaded into Phase 1 instead of sitting behind the UI work.

Output: `BeamSearchSequencer` and a reusable fixture builder that plan 01-05 extends.
</objective>

<constraints>
- **D5 — beam search, width 50. Do NOT implement exact DP as the primary approach.** The
  "visit each vinylID at most once" constraint makes exact DP exponential in the number of
  vinyls. Plan 01-05 adds the wider-beam divergence check; that is the safety net, not an exact
  solver. If you find yourself writing a bitmask over vinyl IDs, stop.
- **D3 — at most one track per `vinylID`. Non-negotiable.** This is the entire reason the app
  exists. The naive implementation gets it wrong when two candidates from the SAME record both
  fall inside the BPM window; there is a named test for exactly that case below.
- **D4 — objective: maximise vinyl count first, tie-break on minimum total Camelot distance.**
  In that order. Never trade a vinyl for a smoother key transition.
- **Exclusion is BPM-driven only.** Camelot distance orders survivors; it never removes a track.
  A track with an unparseable or missing key is still fully eligible.
- Reuse `Camelot` and `BPMRules` from plan 01-03. Do not re-derive wheel arithmetic or the
  fold rule inline — a second copy is a second thing to get wrong.
</constraints>

```swift
public struct BeamSearchSequencer: Sequencing {
    public let beamWidth: Int
    public init(beamWidth: Int = 50)
    public func sequence(candidates: [Track], bpmTolerance: Double) -> SequenceResult
}
```

Algorithm, in order. Follow it — it is the shape the tests are written against.

1. **Normalise.** For each candidate with a non-nil `bpm`, produce a working copy whose `bpm`
   is `BPMRules.fold(bpm)`. Fold before anything else so the gate and the returned badge both
   see the same number. Candidates with nil `bpm` are set aside as *unresolved*.
   Clamp the incoming tolerance with `BPMRules.clampTolerance`.

2. **Sort** the usable candidates ascending by folded BPM. Break ties deterministically:
   BPM, then `camelot ?? ""`, then `id.uuidString`. Determinism here is what makes the
   divergence check in plan 01-05 meaningful — two beam widths must be comparable.

3. **Beam over the sorted order.** Because the list is BPM-ascending and the gate is
   non-decreasing, sorted order is a topological order of the DAG, so a single left-to-right
   pass suffices.

   ```swift
   private struct State {
       var path: [Int]            // indices into the sorted array
       var visited: Set<UUID>     // vinylIDs — D3 lives here
       var lastBPM: Double
       var lastKey: Camelot?
       var distance: Int
   }
   ```

   ```
   var beam: [State] = []
   for (i, c) in sorted.enumerated() {
       var next = beam
       next.append(State(startingAt: i))                      // a path may begin anywhere
       for s in beam where !s.visited.contains(c.vinylID)
                        && BPMRules.canFollow(s.lastBPM, c.folded, tolerance: tol) {
           next.append(s.extended(by: i, cost: edgeCost(s.lastKey, c.key)))
       }
       beam = prune(next)
   }
   ```

   `edgeCost(from:to:)`: `from?.distance(to: to)` when both keys parse, otherwise **0**.
   A missing key contributes nothing rather than a penalty, because key must never influence
   whether a record survives — only how survivors are ordered. Add a `// ponytail:` comment
   naming the ceiling: this mildly favours unknown-key tracks in an exact count tie; revisit
   only if a real set sounds wrong.

   `prune(_:)`: sort by `(path.count desc, distance asc, path.first asc)` and keep the first
   `beamWidth`. The third key is only there to make pruning deterministic.

4. **Winner** = the best state by the same ordering. Empty beam → `SequenceResult.empty`.

5. **notIncluded**, in first-appearance order of the vinyl in the input (stable and testable),
   one row per vinylID not on the winning path:
   - the vinyl has no candidate with a BPM at all →
     `"No BPM yet — resolve it or enter it by hand"`
   - otherwise →
     `"No track within \(formatted(tol)) BPM of the set"` where `formatted` renders 4.0 as "4"
     and 4.5 as "4.5". The tests assert the number appears.

6. Return the winning path's tracks (carrying the folded BPM), the notIncluded rows, and the
   winner's accumulated distance.

Keep the whole type free of `Foundation` randomness, dates, and I/O — it must stay a pure
function so plan 01-05 can hammer it and the purity guard stays green.
