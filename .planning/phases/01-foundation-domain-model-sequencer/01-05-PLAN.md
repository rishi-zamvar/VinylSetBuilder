<objective>
Prove the sequencer is not just correct on a single run but correct as a *re-optimiser* — the
one property the whole product rests on — then make it fast enough and off-main-thread enough
to sit behind a UI, and put a tripwire under the beam width so a silently suboptimal path is
detectable.

CONTEXT.md: *"If that has no test, this phase is not done."* SEQ-10 is the safety net that makes
choosing a heuristic over an exact solver an informed decision rather than a hope.

- `test_givenAVinylOutsideTheBPMWindow_whenSequenced_thenItIsExcluded`
  Vinyl 1 at 170 BPM (`"8A"`), vinyl 2 at 178 BPM (`"9A"`), tolerance 4.0.
  Assert: `sequence.count == 1` and it is vinyl 1's track; `notIncluded.count == 1` and it is
  vinyl 2, carrying the *tempo* reason (the one naming the tolerance, not the "no BPM" one).
  The gap is 8 BPM — twice the tolerance — so this exclusion is unambiguous.

- `test_givenABridgingVinylIsAdded_whenResequenced_thenThePreviouslyExcludedVinylRejoins`
  **THE test.** Take the exact same two vinyls, add vinyl 3 at 174 BPM (`"8B"`), re-run with the
  same tolerance 4.0. Assert ALL of:
    - `result.sequence.count == 3`
    - `result.notIncluded.isEmpty`
    - the BPM order is exactly `[170, 174, 178]`
    - the vinylIDs are exactly `[vinylID(1), vinylID(3), vinylID(2)]` — the rejoined record is
      LAST, not merely present. A test that only asserted `count == 3` would pass on an
      implementation that appended it in the wrong place.
  Add a comment above this test stating, in one line, that it is the phase's success bar.

- `test_givenTheBridgeIsRemovedAgain_whenResequenced_thenTheVinylIsExcludedOnceMore`
  Drop vinyl 3 and re-run. Back to `sequence.count == 1`, vinyl 2 excluded again. This is what
  proves the sequencer has no memory — an incremental implementation would keep 178 in.

- `test_givenTheSameCandidatesInADifferentOrder_whenSequenced_thenTheResultIsIdentical`
  Shuffle the 3-vinyl input with a fixed seed and assert the `SequenceResult` equals the
  unshuffled one. Input order must not affect re-optimisation.

- `test_givenABridgingVinylWhoseOnlyUsableCandidateIsItsSecond_whenResequenced_thenItStillBridges`
  Vinyl 3 carries two candidates: one at 190 (useless) and one at 174 (the bridge). Assert the
  three-track sequence still forms and vinyl 3 contributes its 174 track — the bridge must be
  found among a vinyl's candidates, not just from its first one.

- `test_givenABridgeAddedAtHalfTime_whenResequenced_thenItStillBridges`
  Vinyl 3 at 87 BPM, which folds to 174. Assert the same three-track rejoin. This pins that the
  fold happens before the gate on the re-run path too, not only on a first run.

- `test_givenTwoDisjointBPMIslands_whenBridged_thenBothIslandsMergeIntoOneSequence`
  Vinyls at 168, 170 and vinyls at 180, 182, tolerance 4 → two islands, the sequencer picks the
  better one and excludes the other two. Add a vinyl at 176: assert all five now appear in
  ascending order with an empty `notIncluded`. This is the rejoin case at set scale rather than
  single-record scale.

```swift
public struct BeamDivergenceCheck: Sendable {
    public struct Divergence: Sendable, Hashable, CustomStringConvertible {
        public let narrowWidth: Int
        public let wideWidth: Int
        public let narrowCount: Int
        public let wideCount: Int
        public let narrowDistance: Int
        public let wideDistance: Int
        /// True when the shipped width found exactly as good a set as the wider one.
        public var agrees: Bool { narrowCount == wideCount && narrowDistance == wideDistance }
        public var description: String   // "beam 50: 28 vinyls / 31 hops | beam 150: 28 / 31 — agree"
    }

    public let narrowWidth: Int   // 50 — the shipped width
    public let wideWidth: Int     // 150
    public init(narrowWidth: Int = 50, wideWidth: Int = 150)

    public func compare(candidates: [Track], bpmTolerance: Double) -> Divergence
}
```

`compare` runs `BeamSearchSequencer(beamWidth: narrowWidth)` and
`BeamSearchSequencer(beamWidth: wideWidth)` over the same input and folds both results into a
`Divergence`. Nothing else. It does not log, does not throw, does not mutate — it returns data
and lets the caller decide.

This lives in `Sources/`, not in the test target, because CONTEXT.md leaves the choice open and
a shipped type costs nothing extra while leaving the door open for a future debug screen to call
it. Do **not** wire it into `BeamSearchSequencer` itself — running two beams on every UI
re-sequence would triple the cost of the thing SEQ-09 is trying to keep instant.

Add a `// ponytail:` comment naming the ceiling: agreement on these fixtures is evidence, not
proof of optimality. The upgrade path if it ever disagrees is written in CONTEXT.md D5 — that
disagreement is the signal to revisit the approach, not to bump the width.

  <action>
```swift
public struct AsyncSequencer: Sendable {
    public let inner: any Sequencing
    public init(inner: any Sequencing = BeamSearchSequencer())

    /// SEQ-09: hops off whatever actor called it. The sequencer is a pure function over
    /// Sendable values, so a detached task is safe and needs no isolation of its own.
    public func sequence(candidates: [Track], bpmTolerance: Double) async -> SequenceResult {
        let inner = self.inner
        return await Task.detached(priority: .userInitiated) {
            inner.sequence(candidates: candidates, bpmTolerance: bpmTolerance)
        }.value
    }
}
```

`Task.detached` rather than a plain `Task` is deliberate and load-bearing: under Xcode 26's
`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` default (see STACK.md §3), a plain `Task` spawned
from a main-actor-isolated view model inherits main-actor isolation and would run the beam
search on the main thread — passing a naive "is it async?" test while failing SEQ-09 outright.
The probe test above is what pins this.

No `Sequencing` protocol change. No timeout, no progress reporting, no cancellation plumbing
inside the beam — at sub-second runtimes the task simply finishes. Cancellation is handled by
the caller abandoning the `await`.

Do not add an `actor`. An actor here would serialise sequencing calls behind a single executor
for no benefit, and would make the type non-`Sendable`-transparent to callers.
