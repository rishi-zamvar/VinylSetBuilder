<objective>
Build crate management as a pure value type — list, create, delete, remove a vinyl, and the
per-crate track selection that lets one record live in several crates — then hang the thinnest
possible SwiftUI over it.

Purpose: CRATE-01, CRATE-02, CRATE-06, CRATE-07. The reason this is a `struct` reducer in the
Core package rather than an `@Observable` class in the app target is blunt: **there is no iOS
simulator runtime installed on this machine and no code-signing identity in the repo.** A view
cannot be launched, so any behaviour that lives inside a view cannot be verified tonight. Put
the behaviour in a value type and `swift test` proves all four requirements; leave the views as
dumb projections of that value and there is nothing left in them to get wrong.

Output: `CrateStore` + `Route` + `CrateSummary` + a fixture library, all tested, and four thin
views that compile against the iOS 26 device SDK.
</objective>

  decides *what is true* rather than *what is shown*, move it into `CrateStore`.
- **D8 — Core imports no SwiftUI.** `CrateStore` is a plain `struct`, not `@Observable`. The app
  target owns the one `@Observable` wrapper (`AppModel`) that holds it.
- **D9 — explicit ordering.** `Crate.vinyls` is ordered by each entry's `position`. Deleting a
  vinyl must renumber the survivors contiguously from 0, or Phase 6's persistence inherits gaps.
- **D3/CRATE-07 — selection is per crate, never per vinyl.** `Crate.selectedTrackByVinyl` is the
  only place a selection is stored. Never add a `selectedTrack` field to `VinylEntry`; that is
  precisely the shape that makes CRATE-07 impossible.
</constraints>

```swift
public enum Route: Hashable, Sendable {
    case crateList
    case capture(crateID: UUID)     // CRATE-02 lands here; CRATE-05 returns here
    case crateDetail(crateID: UUID)
}

public struct CrateSummary: Identifiable, Sendable, Hashable {
    public let id: UUID
    public let name: String
    public let recordCount: Int
}

public struct CrateStore: Sendable, Equatable {
    public private(set) var crates: [Crate]     // newest first
    public var route: Route

    public init(crates: [Crate] = [], route: Route = .crateList)

    // CRATE-01
    public var summaries: [CrateSummary] { crates.map { .init(id: $0.id, name: $0.name, recordCount: $0.recordCount) } }
    public func crate(_ id: UUID) -> Crate?

    // CRATE-02 — creating and routing are ONE operation, never two
    @discardableResult
    public mutating func createCrate(named rawName: String, now: Date = Date()) -> UUID

    // CRATE-06
    public mutating func deleteCrate(_ id: UUID)
    public mutating func removeVinyl(_ vinylID: UUID, from crateID: UUID)

    // CRATE-07
    public mutating func addVinyl(_ vinyl: VinylEntry, to crateID: UUID)
    public mutating func selectTrack(_ trackID: UUID, forVinyl vinylID: UUID, in crateID: UUID)
    public func selectedTrack(forVinyl vinylID: UUID, in crateID: UUID) -> UUID?

    public mutating func open(_ crateID: UUID)
    public mutating func closeToList()
}
```

Notes that matter:

- `createCrate` takes `now: Date = Date()` so tests can pin `createdAt` and the "newest first"
  ordering assertion is deterministic. Never read the clock inside the store without a seam.
- Every mutator resolves the crate through a single private
  `mutating func withCrate(_ id: UUID, _ body: (inout Crate) -> Void)` that no-ops on an unknown
  ID. One guard, not six — the unknown-ID tests all route through it.
- `removeVinyl` does three things in one place: drop the entry, renumber survivors' `position`
  from 0, and clear that vinyl's key from `selectedTrackByVinyl`. Splitting these across call
  sites is how the dangling-selection bug gets in.
- `deleteCrate` checks whether `route` points at the deleted ID and falls back to `.crateList`.

`Crate.recordCount` already exists on the domain type from 01-01 — call it, do not recompute
`vinyls.count` here.
