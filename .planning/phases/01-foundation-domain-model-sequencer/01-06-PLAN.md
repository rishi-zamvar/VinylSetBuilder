<constraints>
- **`CrateStore` lives in the Core package, not the app target.** It is plain observable state
  with no UI framework in it, and putting it in Core is what lets its behaviour be tested by
  `./Scripts/test.sh` with no simulator and no XCUITest. `import Observation` is permitted by
  the purity guard; `import SwiftUI` is not. The views in `App/` stay thin — they render and
  dispatch, they never mutate an array directly.
- **No persistence.** `CrateStore` holds its crates in memory, seeded from `FixtureCrates`.
  SwiftData is Phase 6 (PERS-01..04). Do not add a `@Model` class here; do not add a
  `ModelContainer`. The store's shape must map cleanly onto one later, which is why plan 01-01's
  types already use `position: Int` and scalar arrays.
- **No camera.** `CaptureStubView` is a placeholder. AVFoundation arrives in Phase 2 (CAP-01..06).
  Do not import it, do not request camera permission, do not add `NSCameraUsageDescription`.
- **CRATE-02 says "land directly in the camera".** In Phase 1 that means landing directly on
  `CaptureStubView` — one navigation step, not back to the list with a "now open your new
  crate" step. The flow shape is the requirement; the camera behind it is Phase 2's.
- After adding files under `App/`, run `./Scripts/regenerate-project.sh` — XcodeGen globs the
  folder, so no project file is hand-edited.
</constraints>

CONTEXT.md gives discretion on the fixture shape but sets a hard floor: it must exercise the
excluded/unresolved path and the rejoin-on-add behaviour, **not just a happy path**. A fixture
where everything resolves and everything sequences would make plan 01-07's UI look correct
while hiding both of the states the design is actually about.

`FixtureCrates.demoCrate` — "Friday Night", 6 vinyls, all keys real Camelot codes, tolerance
4.0. Concretely:

| Vinyl | Candidates (BPM / key) | Role in the fixture |
|-------|------------------------|---------------------|
| 1 | 170 / 8A, 171 / 9A | two candidates on one record — proves the one-per-vinyl rule visibly |
| 2 | 174 / 8B | ordinary |
| 3 | 174 / 5A | ties with vinyl 2 on BPM, differs on key — the Camelot tie-break is visible |
| 4 | 177 / 9A | ordinary |
| 5 | nil (`resolutionState == .failed`, `failureReason` set) | **unresolved** — no BPM at all |
| 6 | 186 / 3A | **excluded** — 9 BPM above 177, outside tolerance until the bridge is added |

`FixtureCrates.bridgingVinyl` — a 7th vinyl at 181 / 9A, deliberately **not** in `demoCrate`.
`CaptureStubView`'s "Add a record" button appends it, which turns vinyl 6 from excluded into
included. That is the rejoin demonstrated in the UI, matching the SEQ-08 test in plan 01-05.

`FixtureCrates.emptyCrate` — "New Crate", zero vinyls, so the empty state is designed rather
than discovered on device.

`FixtureCrates.sharedVinyl` — one `VinylEntry` with three candidates (172 / 8A, 176 / 11A,
180 / 2A) referenced by two crates, for plan 01-07's CRATE-07 work.

Give every track a real-looking artist/title (jungle/DnB flavoured) — a list of "Fixture Track
1..6" makes the sequenced view impossible to eyeball for correctness.

  compaction matters because Phase 6 persists these integers.
- `test_givenCrate_whenVinylRemoved_thenItsSelectionIsAlsoCleared`: `selectedTrackByVinyl` must
  not retain an entry for a vinyl no longer in the crate. A stale selection is exactly the kind
  of orphan that survives into Phase 6's store and is painful to find later.
- `test_givenBridgingVinylAdded_whenAdded_thenCrateHasSevenRecords`: the append path
  `CaptureStubView` uses.

  <action>
```swift
import Observation

@Observable
@MainActor
public final class CrateStore {
    public private(set) var crates: [Crate]

    public init(crates: [Crate] = [])
    public static func previewSeeded() -> CrateStore     // FixtureCrates.demoCrate + emptyCrate

    @discardableResult
    public func createCrate(name: String) -> Crate.ID
    public func deleteCrate(id: Crate.ID)
    public func addVinyl(_ vinyl: VinylEntry, to crateID: Crate.ID)
    public func removeVinyl(vinylID: UUID, from crateID: Crate.ID)
    public func crate(_ id: Crate.ID) -> Crate?
    public func setTolerance(_ value: Double, for crateID: Crate.ID)   // used by plan 01-07
    public func setManualOrder(_ order: [Track.ID]?, for crateID: Crate.ID)  // used by plan 01-07
    public func setSelectedTrack(_ trackID: UUID, forVinyl vinylID: UUID, in crateID: Crate.ID)
}
```

`crates` is `private(set)` — every mutation goes through a named method, so plan 01-07's views
cannot reach in and reorder an array behind the store's back, and the Phase-6 persistence hook
has exactly one set of call sites to attach to.

`removeVinyl` must: drop the vinyl, compact the remaining `position` values to 0..<n, clear the
`selectedTrackByVinyl` entry, and drop any `manualOrder` entries pointing at that vinyl's tracks.
That last one is the wiring people forget; the test above catches the selection half and plan
01-07's reorder work depends on the `manualOrder` half.

`setTolerance` clamps via `BPMRules.clampTolerance`.
