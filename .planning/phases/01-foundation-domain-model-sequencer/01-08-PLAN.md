<objective>
The crate screen: open a crate and see its sequenced running order, drag to override it, pull a
slider to loosen or tighten the tempo gate and watch the set re-derive, and tap Add More to go
back to capture.

Purpose: CRATE-03, CRATE-04, CRATE-05, SEQ-05. This is where the sequencer becomes the product.
The hard part is not the list — it is the interaction between a *manual* order and a sequencer
that fully re-derives on every change. Those two things are in direct tension, and the tension
gets resolved here, in a tested value type, rather than being discovered later as a bug where a
user's careful drag silently evaporates when they add one more record.

Output: `CrateDetailModel`, `CrateStore.addMore`, and the crate detail screen.
</objective>

<constraints>
- **The sequencer stays pure and stays memoryless.** `CrateDetailModel` never mutates a
  `SequenceResult`; it *applies* one. SEQ-08's rejoin behaviour depends on every re-run being a
  full re-derivation — if you cache a previous ordering inside the model and merge into it, you
  break the phase's success bar from the far side.
- **D9 — ordering is explicit.** The manual override is persisted as `Crate.manualOrder: [Track.ID]?`,
  a scalar array. Never reorder `crate.vinyls` in place to express a manual order, and never rely
  on the array order of anything else surviving Phase 6's SwiftData mapping.
- **SEQ-05 — tolerance is 3.0...6.0, default 4.0**, clamped with `BPMRules.clampTolerance`. It
  lives on the `Crate` (`bpmTolerance`), not on the model and not in the view, because it must
  survive navigating away and, in Phase 6, quitting the app.
- **D8 — Core imports no SwiftUI.** `CrateDetailModel` is a plain `struct` with synchronous
  mutators. The async hop is the view's job, using `AsyncSequencer` from plan 01-05.
- **D7 — one not-included bucket.** Use `CrateRows` from plan 01-07 as-is. Do not build a second
  row type and do not split the bucket here.
- No simulator runtime, no signing identity. `Scripts/build-app.sh` (device SDK,
  `CODE_SIGNING_ALLOWED=NO`) is the app target's only gate. Never add a simulator destination.
</constraints>

The reconciliation rule — write it as a comment above the code, because it is the one piece of
this phase a future reader will not be able to infer:

> `apply(_:)` re-derives which tracks are IN the set (the sequencer's job, always authoritative).
> `manualOrder` only re-derives the ORDER of the ones that are in. Concretely: filter
> `manualOrder` down to IDs still present in `result.sequence`, then append any newly-sequenced
> IDs, in the sequencer's own order, at the end. Membership is the sequencer's; arrangement is
> the user's.

That rule is what makes CRATE-04 and SEQ-08 coexist. Adding a record still triggers a full
re-optimisation and a previously excluded vinyl still rejoins — it simply lands at the bottom of
a manually ordered list instead of in its computed slot, and the screen tells the user their
order is custom and offers one tap to restore the sequenced one.

`moveRows` computes the new order from the *currently displayed* rows (so a drag on a
manually-ordered list composes correctly), then writes it to `crate.manualOrder` and rebuilds
`rows`. Do not reorder `crate.vinyls`.
